## Current working flow

The active app already has guest checkout, server-authoritative offers, idempotent order creation, separate payment/provisioning/voucher states, voucher timer from first login, local staff sessions, owner/admin/partner views, partner masking, 50 synthetic partners, and demo controls. A customer order token no longer authorizes payment/provisioning/WhatsApp transitions. Current `Site` doubles as one hotspot per Partner; there is no explicit Provider/Location/Hotspot hierarchy, staff assignment, QR, inventory depletion, or operational alert/incident/support center. Current admin access is global. The order `connect` action can activate a voucher directly from an order token, so activation authority needs tightening in V2.

## Constraints and stop line

The revised captive route identifies hotspot context by URL/demo redirect. It does not inspect the device SSID. QR scanning uses camera capability only after permission and never grants network access without backend credential checks. Online payments are centrally modeled under PT. SSS, but remain simulation. Partner commission percentages remain labeled historical demo assumptions. No production migration, live provider call, real customer data, router action, deploy, or remote push occurs in this batch.
